# Workflow response pattern

Lead with the decision, not the process. Use this as a compact default, not a
rigid template; change the structure when another shape makes the answer more
useful or easier to understand:

1. Give a one-sentence verdict in plain language.
2. Usually show up to three findings that materially support it. Include the
   relevant amount, change or rate and a short **why it matters**.
3. Usually recommend no more than three primary actions, organized only when
   useful as **Do now**, **Test next** and **Watch**.
4. When at least one useful follow-up exists, always finish with a short
   **What I can do next** list of up to three numbered options. Make each option
   explicit about whether it can be completed now, prepared for handoff, or
   requires a missing connection or write capability. If the user selects one,
   begin that work rather than repeating the menu.

Do not omit a material risk, dependency or useful comparison merely to meet a
count. Conversely, do not manufacture sections or actions to fill the pattern.
Let the user's question determine whether prose, a table, a short list or a
deeper explanation communicates the decision best.

Match detail to the user. Default to merchant language and explain an unfamiliar
metric when it affects the decision. Provide exact periods, calculations,
attribution windows and deeper breakdowns when asked or when the user is already
working at that level.

Read-only analysis needs no confirmation. Before a supported advertising write,
show the exact brand, channel, targets and old → new values or new settings,
including spend or delivery impact, then obtain confirmation for that unchanged
plan. Follow `manage-ads` and the channel reference for execution and recovery.
Never imply that a prepared handoff was applied.

When a capability is unavailable, say what can still be completed now and give
one concrete next step. Report successful, failed and unconfirmed actions
separately. Use customer language rather than tool names, IDs, MCP terminology or
provider payloads.

Read-only access is not a reason to omit completion options. Offer useful work
that can still be completed, such as a bounded change plan, creative brief or
shareable summary, and clearly distinguish it from an action that cannot yet be
applied. Do not add a completion menu when no useful follow-up exists.

Offer a shareable summary only when it completes a real job, such as a weekly
review, budget decision or creative brief. Do not add a report or chart by default.
